HOW THE AI MONITORS AND STRUCTURES THE UNITY 3D DATA LAYER

1. THE UNITY RUNTIME MEMORY TREE (WHAT DATA EXISTS)

Every Gorilla Tag clone running inside the Unity 3D engine stores its active variables in a structured hierarchy. When a modder attempts to use a tool like Il2CppDumper, they are trying to read this specific layout. Your AI needs to understand this data structure to monitor it:

- UnityEngine.SceneManagement (The Environment Data)
  * Contains the active 3D GameObject instances, Mesh Colliders, and Layer masks (e.g., Layer 9 for environment collision, Layer 10 for Gorilla players).

- GorillaLocomotion.Player (The Movement Data)
  * Transform Component: Stores Vector3 data for position (X, Y, Z) and rotation.
  * Rigidbody Component: Handles velocity vectors, acceleration, gravity scales, and mass constants.
  * Sphere Colliders: Tracks the exact radius and spatial offsets of the hand triggers.

- Photon.Pun.PhotonNetwork (The Network Data)
  * Custom Room Properties: Key-value data tables synced across all connected clients.
  * Photon View IDs: Unique integer trackers mapped to every individual monkey avatar in the lobby.


2. THE DATA EXTRACTION MECHANICS (HOW THE DATA IS SCRAPED)

To catch modders who are actively changing memory values inside `libil2cpp.so` or injecting scripts via BepInEx, the AI anti-cheat can run automated internal data sweeps at the engine level:

- Reflection & Type Checking:
  * The AI can scan the Unity assembly domain for unknown or unauthorized Types. If a modder drops a rogue `.dll` into the game, it will register new classes that do not exist in the official build manifest.

- Direct Component Querying:
  * Using functions like `GameObject.FindObjectsOfType<Player>()`, the AI continuously pulls the active data profiles of every player object in the scene to check if multiple instances of the player script are running (a common indicator of ghost/cloning hacks).
